# Отчет: Производительность RabbitMQ vs Redis

## 1. Цели исследования

Провести сравнительный анализ двух брокеров сообщений - `RabbitMQ` и `Redis` - в контролируемых условиях для выявления:

- Максимальной пропускной способности
- Влияния размера сообщений на производительность
- Критической точки деградации при увеличении нагрузки

### Параметры тестирования

Для обеспечения объективности сравнения использовались идентичные условия:

- Формат сообщений: JSON с метаданными
- Конфигурация: 2 производителя, 2 потребителя
- Ресурсы: 1 CPU, 512 MB RAM на брокер
- Длительность одного теста: 10 секунд (быстрый режим)

Варьируемые параметры:

- Размер сообщения: `128 байт`, `1 КБ`
- Интенсивность: `1000 msg/s`, `5000 msg/s`

## 2. Архитектура тестового стенда

```
[Производители (2)] → [Брокер] → [Потребители (2)]
```

Последовательно тестировались:

1. RabbitMQ (single instance)
2. Redis (single instance)

Инструмент: собственный генератор нагрузки на Python с async IO.

## 3. Измеряемые показатели

### Основные метрики

- **Пропускная способность**: сообщений в секунду (отправка/прием)
- **Задержки**: среднее, 95-й перцентиль, максимум (в миллисекундах)
- **Надежность**: отправлено, получено, потеряно, ошибки отправки
- **Состояние очереди**: размер backlog после завершения теста
- **Деградация**: интегральный показатель работоспособности

## 5. Анализ результатов

### 5.1 Пропускная способность

**Наблюдение:** При высокой интенсивности (5000 msg/s) Redis демонстрирует преимущество:

- RabbitMQ: ~2820-2830 сообщений/сек
- Redis: ~2987-3000 сообщений/сек

**Вывод:** Redis обеспечивает на ~5-6% большую пропускную способность в условиях высокой нагрузки.

### 5.2 Влияние размера сообщения

**Наблюдение:** Увеличение размера с 128 байт до 1 КБ:

- RabbitMQ: практически не влияет на производительность
- Redis: также демонстрирует стабильность

**Вывод:** В диапазоне 128Б - 1КБ оба брокера показывают линейную масштабируемость. Для тестирования критических размеров требуется запуск полного набора с payload 10 КБ и 100 КБ.

### 5.3 Задержки обработки

**Наблюдение:** Redis показывает меньшие задержки во всех сценариях:

При 5000 msg/s и 128 байт:
- RabbitMQ: среднее 0.39 мс, P95 0.45 мс
- Redis: среднее 0.19 мс, P95 0.21 мс

**Вывод:** Redis обеспечивает в 2 раза меньшие end-to-end задержки.

### 5.4 Точка деградации

**Наблюдение:** Ни один из брокеров не показал признаков деградации в рамках быстрого теста:

- Backlog = 0 во всех случаях
- Потери сообщений отсутствуют
- P95 значительно ниже порогового значения (200 мс)
- Ошибки отсутствуют

**Вывод:** Для достижения точки деградации требуется более высокая нагрузка (10000+ msg/s) или большие размеры сообщений.

## 6. Выводы

1. **Пропускная способность:** Redis превосходит RabbitMQ на ~5-6% при интенсивности 5000 msg/s

2. **Размер сообщений:** В диапазоне 128Б - 1КБ оба брокера демонстрируют стабильную работу без деградации

3. **Задержки:** Redis обеспечивает в 2 раза меньшие latency во всех тестовых сценариях

4. **Надежность:** Оба брокера обеспечили 100% доставку без потерь и ошибок

5. **Критическая нагрузка:** В рамках быстрого теста не достигнута ни для одного из брокеров. Для полного анализа требуется запуск с параметрами --duration 30 и полным набором rates/sizes

6. **Рекомендации по применению:**
   - **Redis**: предпочтителен для сценариев, требующих минимальных задержек и высокой пропускной способности при небольших сообщениях
   - **RabbitMQ**: более подходит для сложных сценариев маршрутизации, требований к гарантиям доставки и интеграции с AMQP-экосистемой
